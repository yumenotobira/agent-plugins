# Pull Request の書き方

この開発フローでは、コミットや PR の作成も、その内容の確認も AI が行う。人間は基本的にレビューしない。そのため PR の説明は、次の 2 人の読み手のための記録として書く。

- **人間**: 細部を読まずに、どういう設計にしたのかを短時間で把握したい。→「設計の要約」
- **あとから来る AI**: 変更・拡張・修正をするときに、なぜその設計なのかを理解して、意図を壊さずに作業したい。→「設計の理由」

差分を読めば分かることは繰り返さない。差分からは読み取れない設計と、その理由を書く。

## 手順

1. **ブランチの状態を確認する**:
   - デフォルトブランチ上にいる場合は、作業ブランチを切ってからコミットする。
   - `git status` でコミット漏れがないか確認する。
   - `git log <base>..HEAD` と `git diff <base>...HEAD` で、PR に含まれる変更をすべて把握する。最新のコミットだけを見て書かない。
2. **差分を確認する**: デバッグ用のコード、不要なファイル、秘密情報、無関係な変更が混ざっていないか確認する。混ざっていれば取り除くか、ユーザーに伝える。
3. **関連 issue を確認する**: 対応する issue があれば `gh issue view <番号>` で読み、完了条件を把握する。
4. **リポジトリの慣習に合わせる**:
   - `.github/pull_request_template.md`（または `.github/PULL_REQUEST_TEMPLATE/`）があれば、そのテンプレートを優先する。ただし「設計の要約」と「設計の理由」がなければ追加する。
   - 言語、タイトルの書き方（Conventional Commits など）、ラベルは既存の PR（`gh pr list --state merged --limit 10`）に合わせる。
   - ラベルは `gh label list` にある既存のものだけを使う。
5. **下書きする**: テンプレートがなければ [references/template.md](references/template.md) を使う。
6. **作成する**: ユーザーが PR の作成を依頼している場合はそのまま作成してよい。説明文の下書きだけを頼まれた場合は、作成せずに提示する。
   - ブランチが未 push なら `git push -u origin <branch>` する。
   - 本文はファイルに書いて `gh pr create --base <base> --title "..." --body-file <file>` で作成する。
   - 作業途中の場合は `--draft` を付ける。
   - 作成後は URL を報告する。

## タイトル

- 何をする PR かがタイトルだけで分かるようにする。動詞で始める（`Add ...` / `Fix ...` / `〜を追加する` など）。
  - 悪い例: `修正`、`feature/login`
  - 良い例: `パスワードに記号を含むとログインできない問題を修正`
- 50〜70 文字程度を目安にする。
- リポジトリに慣習（`feat:` などの接頭辞、issue 番号）があれば合わせる。

## 本文の原則

- **設計の要約は必須**: 人間が数十秒で読めるように、どういう構成・仕組みにしたのかを要約する。実装の細部やファイルの列挙ではなく、全体像（何がどこにあり、どう動くか）を書く。
  - 処理の流れ、状態遷移、コンポーネント間のやり取り、依存関係など、図にできるものは Mermaid で書く。文章で説明するより図を優先する。
  - ディレクトリ構成はツリーで書く。
- **設計の理由は必須**: なぜその設計にしたのかを書く。あとから AI が読んで、意図を誤解せずに変更できることが目的。次の項目を分けて書く。
  - **選んだ理由**: なぜこの設計・実装方法にしたのか。
  - **前提にした制約**: 設計の前提になった要件・制約（運用の前提、外部仕様、他の箇所が依存している挙動など）。変更するときに守るべきことはここに書く。
  - **意図的にやっていないこと**: スコープ外にしたこと、割り切っていること。
  - 自明な変更（typo 修正など）でも省略せず、「設計の変更なし」のように一行書く。
- **issue と紐づける**: マージで issue を閉じる場合は `Closes #123` と書く。部分対応なら `Refs #123` にして、閉じないようにする。issue に書いてある背景は繰り返さず要点だけにする。
- **issue の完了条件と対応させる**: 関連 issue に完了条件があれば、それぞれがどう満たされたかが分かるようにする。
- **確認したことを書く**: 実行したテストや動作確認の内容と結果を書く。確認していないことを確認済みとして書かない。マージ後でないと確認できないことは、未チェックの項目として残す。
- **小さく保つ**: 1 PR は 1 つの目的に絞る。無関係な変更（ついでのリファクタリング、フォーマット変更など）は別 PR に分ける。
- **秘密情報を書かない**: トークン、パスワード、個人情報などを本文やログに含めない。

## 既存 PR の説明を書き直すとき

- 追加のコミットで設計が変わった場合は、「設計の要約」と「設計の理由」を最新の状態に更新する。本文だけ読めば最新の設計が分かるようにする。
- 編集は `gh pr edit <番号> --body-file <file>` で行う。

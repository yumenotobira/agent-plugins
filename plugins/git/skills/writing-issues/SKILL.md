# Issue の書き方

issue は「あとから読んだ人（未来の自分や AI agent を含む）が、追加の質問なしに着手できる」ことを目標に書く。

## 手順

1. **既存の issue を確認する**: `gh issue list --search "<キーワード>" --state all` で重複や関連 issue を探す。重複があれば新規作成せず、ユーザーに伝える。
2. **リポジトリの慣習に合わせる**:
   - `.github/ISSUE_TEMPLATE/` があればそのテンプレートを優先する。
   - 言語（日本語/英語）、タイトルの書き方、ラベルの使い方は既存 issue に合わせる。
   - ラベルは `gh label list` にある既存のものだけを使う。勝手に作らない。
3. **種類を決めて下書きする**: 下の「種類別のテンプレート」から該当する references のファイルを読んで使う。
4. **ユーザーに下書きを見せてから作成する**: issue の作成は外部に公開される操作なので、明示的に「作成して」と言われていない限り、下書きを提示して確認を取る。
5. **作成する**: 本文はファイルに書いて `gh issue create --title "..." --body-file <file>` で作成する（シェルのエスケープ事故を防ぐため）。作成後は URL を報告する。

## タイトル

- 何が問題か / 何を実現したいかが、タイトルだけで分かるようにする。
- 具体的に書く。「バグ修正」「改善」のような曖昧な語だけにしない。
  - 悪い例: `ログインのバグ`
  - 良い例: `パスワードに記号を含むとログインが 500 エラーになる`
- 50 文字程度を目安に、詳細は本文へ。
- `[Bug]` などの接頭辞は、リポジトリに慣習がある場合だけ付ける（種類はラベルで表す）。

## 本文の原則

- **事実と推測を分ける**: 観測した事実（エラー文、ログ、再現手順）と、原因の推測・解決案は別のセクションに書く。推測は「〜と思われる」と明記する。
- **完了条件を書く**: 何をもって close できるかをチェックリストで書く。検証可能な表現にする。
- **1 issue = 1 PR で閉じられる大きさ**: 大きいものは親 issue にタスクリストを置き、子 issue に分割する。
- **コンテキストを残す**: 関連 issue / PR / ドキュメントへのリンク、該当コードの場所（`path/to/file.ts:42` やパーマリンク）を書く。
- **秘密情報を書かない**: トークン、パスワード、個人情報、社内 URL などはマスクする。ログを貼る前に確認する。
- 長いログは `<details>` で折りたたむ。

## 種類別のテンプレート

issue の種類を決めたら、該当するファイルを読んでテンプレートに沿って書く。リポジトリに issue テンプレートがある場合はそちらを優先する。

| 種類 | 使う場面 | テンプレート |
|---|---|---|
| バグ | 不具合、エラー、期待と異なる動作 | [references/bug.md](references/bug.md) |
| 機能追加・改善 | 新機能、既存機能の改善、仕様変更 | [references/feature.md](references/feature.md) |
| タスク | リファクタリング、調査、依存更新、雑務 | [references/task.md](references/task.md) |

## 既存 issue を書き直すとき

- 元の意図を変えない。変える場合はユーザーに確認する。
- 議論で決まったことは本文に反映し、本文だけ読めば現状が分かるようにする。
- 編集は `gh issue edit <番号> --body-file <file>` で行う。
